# 真实项目代码评审案例

> 参考来源：Google Engineering Practices — Code Review
> https://github.com/google/eng-practices
> 说明：以下条目按“评审优先级”整理为可检索的检查项，用于约束生成与审核。

## 评审目标与优先级

- 评审的首要目标是让代码库的整体健康度持续提升，而不是追求“完美代码”。
- 优先检查设计、功能正确性、复杂度与测试；命名、注释、格式属于次要问题。
- 不因个人风格偏好阻断变更；纯风格建议应标注为“建议/Nit”，由作者决定是否处理。
- 能明确改善可维护性、可读性与可理解性的变更，不应因为细节不完美而长期搁置。

## 设计是否合理

- 变更是否放在正确的模块与层次，是否与现有架构和调用方式一致。
- 是否引入了不必要的抽象、包装层或跨层依赖。
- 一次变更只解决一个问题；功能修改不要和大规模格式化、重命名混在一起。
- 新增能力应先满足当前需求，而不是为假设的未来场景预留复杂扩展点。

## 功能与并发正确性

- 代码是否真正实现了需求与验收标准，而不是只让示例输入通过。
- 边界、空值、异常路径是否覆盖；错误是否被正确处理而不是被吞掉。
- 并发代码要检查竞态、死锁与共享可变状态；优先用不可变数据或加锁消除风险。
- 评审者不能只看 diff，要结合完整文件与调用链判断变更是否破坏原有行为。

## 复杂度与过度设计

- 单个函数、类或一行表达式是否能在短时间内被读者理解。
- 嵌套层级、分支数量、参数数量是否过多；超过约 40 行或 3 层嵌套应考虑拆分。
- 是否存在“为未来可能需要的功能”而增加的泛化逻辑。
- 复杂实现应给出理由；如果无法快速解释清楚，通常说明实现需要简化。

## 测试是否有效

- 实现与测试应在同一次变更中提交，测试文件与实现文件分离但语义对应。
- 测试必须能在实现出错时失败；只断言“不为 None”“大于 0”属于弱断言。
- 覆盖正常路径、空输入、边界值、非法输入与异常类型。
- 测试自身也要可维护：用例名表达场景与预期，避免复制粘贴和依赖执行顺序。

## 命名、注释与文档

- 名字要表达意图，长度足以说明用途，又不至于难读。
- 注释解释“为什么这样做”，不要复述代码“做了什么”；过期注释必须同步删除。
- 公开函数写 docstring，说明参数、返回值与可能抛出的异常。
- 变更影响构建、测试或使用方式时，同步更新 README 与相关文档。

## 评审粒度与评论写法

- 评审范围要适中：逐行阅读变更，同时查看完整上下文与系统影响。
- 每条评论给出触发条件、后果与可执行的修改建议，避免只说“这样不好”。
- 同一根因只报一次，不重复罗列表面现象。
- 区分“必须修改”和“建议优化”；阻断问题必须给出明确修复方向。
- 发现优点也应指出，评审的目的是改进代码，而不是单纯挑错。
