# 本项目的代码生成与交付约定

## 函数契约

- 实现代码的函数名必须与需求确认结果中的 function_name 完全一致，不得改名或加包装层。
- 只实现需求要求的公开函数，不额外暴露未要求的全局变量与副作用。
- 返回值类型与需求中的 outputs 一致；空输入、非法输入按 edge_cases 的约定返回。
- 需要抛出异常时，抛出含义明确的内置异常类型，并给出可读的错误信息。

## 依赖与实现约束

- 默认只使用 Python 标准库，不引入第三方依赖；确有需要须在需求中显式说明。
- 禁用 eval、exec、compile 及动态导入用户可控的模块名。
- 不使用网络请求、数据库连接、系统命令等外部副作用，除非需求明确要求。
- 不在代码里硬编码密钥、令牌、绝对路径；不写入与功能无关的调试输出。

## 工程文件约定

- 每次运行在独立目录中写入 solution.py 与 test_solution.py，两者同名约定不可更改。
- 测试通过 `from solution import 函数名` 导入被测实现，不复制实现代码。
- 测试文件只放用例，不放业务逻辑；辅助构造数据的方法写在测试文件内并以 `_` 开头。
- 生成的代码必须能通过语法编译，且不产生 Ruff 规范类阻断问题。

## 审核与收敛口径

- 严重等级三级：阻断（可导致安全事故或必然崩溃）、主要（功能错误或关键边界缺失）、次要（规范与可读性）。
- 审核结论同时参考静态工具（Ruff、Bandit、ast）与 LLM 语义审核，两者互补而非互相覆盖。
- 收敛条件：无阻断、无主要问题，且 pytest 全部通过（没有测试时视为测试维度不参与判定）。
- 低置信度的 LLM 问题会被过滤，静态工具发现的问题全部保留，避免误报影响修复方向。

## 修复原则

- 只针对已列出的问题做最小化修改，不顺手重构无关代码。
- 修复后函数名、公开接口、既有测试语义保持不变。
- 优先修根因（边界守卫、类型校验、异常处理），而不是在测试里放宽断言掩盖问题。
